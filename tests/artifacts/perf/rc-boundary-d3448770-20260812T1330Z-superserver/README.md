# RC boundary rerun — control b612eb7b5 vs RC d34487705 (bd-dqdoe release gate)

Host: superserver (AMD EPYC 7282, 64 cores), taskset CPUs 40-47 (claimed on
bd-dqdoe), 2026-08-12 ~12:39-13:30Z, load 4-9/64 throughout. Orchestrated by
`rc_boundary_rerun.sh` (in this pack).

## Protocol

- Clean detached git worktrees at each SHA; dirty-tree refusal enforced.
- Sequential citation-grade `release` builds: `cargo build -vv --locked
  --offline --target x86_64-unknown-linux-gnu`, full canonical profile
  environment forced (all 16 values incl. explicitly-empty rustc wrappers and
  `CARGO_ENCODED_RUSTFLAGS`), `LIBSQLITE3_FLAGS=-DSQLITE_ENABLE_MATH_FUNCTIONS`,
  64-hex build nonce, SHA-bound `cargo -vv` log receipt.
  - RC-side runtime provenance: **receipt-clean** — `git d34487705 dirty=false`,
    `verbose_build_log_verified=true` (nonce proven in the final binary's rustc
    invocation); residual `validation_errors` are only the permanent
    design/C-reference scope notes, so runs require
    `--allow-unverified-provenance` by design (comprehensive measurements are
    diagnostic-grade per the harness's own contract).
  - Control-side vintage limitation (stated, not concealed): b612eb7b5
    pre-dates the provenance apparatus (no fsqlite-e2e build.rs, no
    `--allow-unverified-provenance` flag). The control arm is receipted by
    clean-worktree SHA + deterministic ELF sha256 (bit-identical across two
    independent rebuilds) + kept build log.
- Campaign: per family (`--filter read`, `--filter concurrent`), 10 ABBA
  blocks of ctrl/rc/rc/ctrl invocations = 20 invocations/arm, 80 total,
  zero failures. All 80 JSON artifacts in `rc-boundary-runs.tar.zst`.

## Verdict (see verdict.txt for the full table)

Statistic: within-invocation paired F/C median ratio per cell (unit-safe),
compared across vintages (DiD = F/C@rc ÷ F/C@ctrl). Cross-vintage raw
`median_ms` is NOT comparable for several cells because the harness itself
changed measurement semantics between the SHAs (bd-zavyn/bd-1qjsy 64-query
tiny-cell batching — C_drift ~52-57x on count/pk/secondary is the unit change,
not host drift; FD1RA pairing + iteration floor 3-10→20-40).

READ (21 cells, 20/arm): at the RC SHA FrankenSQLite is FASTER than C SQLite
in 20/21 cells (F/C 0.08-0.70). C-drift null PASSES on all unit-stable cells
(0.94-1.10). DiD vs control is >1 on most cells but is confounded by the
protocol changes above; the clean-null receipt is the hoisted secondary-lookup
family (DiD 1.01-1.02 at all row counts). Named residuals:
- PK point-lookup DiD ~1.25 → bd-qcgn2 (known engaged-lane residual).
- 100-row SUM+GROUP BY: the ONLY absolute red (F/C@rc 2.22, DiD 3.4) → filed
  as its own bead from this run.

CONCURRENT (2t/4t/8t, 20/arm, file-backed WAL, NORMAL): absolute F medians
IMPROVED at RC: 2t 25.9→13.6ms (0.53x), 4t 51.3→35.9ms (0.70x), 8t
89.6→95.0ms (1.06x, within this section's documented disk-noise CV). F/C@rc:
2t 1.44, 4t 1.04, 8t 0.73 (F 1.4x faster at 8 writers). The adverse 2t/4t DiD
is driven by the C arm's medians dropping under the modern paired protocol
(C 43.1→9.5ms at 2t), not by an F regression — F improved absolutely.
Zero aborts, zero BusyRecovery in 80/80 invocations: bd-b4mwn's fix holds at
the RC SHA under the formal protocol. Per the harness's own provenance note,
cite `mt_mvcc_bench` (bd-x5gzk), not these rows, for concurrent-writer speed
claims.

T16: comprehensive-bench has no 16-writer cell (`CONCURRENT_THREAD_COUNTS =
[2,4,8]` at both SHAs); the 16-writer axis is owned by the bd-dqdoe.1
mt-mvcc-matrix lane. Patching the constant would have dirtied the tree and
voided provenance, so it was not done.
